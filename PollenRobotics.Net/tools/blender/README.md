# Robot models

The simulator's three robots are glTF models generated by Blender from the photographs in
[`images/`](../../images). This directory holds the recipe; the `.glb` files under
`apps/PollenRobotics.Net.Simulator/wwwroot/models/` are its output.

**Edit the Python, not the `.glb`.** A binary that cannot be diffed and cannot be regenerated is a
dead end the first time a proportion needs correcting.

## Build

```bash
blender --background --factory-startup --python tools/blender/build_models.py
```

Takes about twenty seconds for all three. Options come after a bare `--`:

```bash
# One robot, with a render to compare against its reference photograph.
blender --background --factory-startup --python tools/blender/build_models.py -- \
  --only reachy-mini --preview

# Somewhere other than wwwroot/models.
... -- --out /tmp/models
```

Previews land in `tools/blender/preview/` and are git-ignored: they are for checking a model, not
for shipping.

Blender 5.2 was used. Anything from 4.2 up should work - the only version-sensitive line is the
EEVEE engine identifier, which the preview code probes for rather than hard-coding.

## Files

| File | Contents |
|---|---|
| `common.py` | Modelling helpers: rounded boxes, lathes, tubes, helices, joints, export |
| `reachy_mini.py` | Bell body, Stewart neck, slab head, sprung antennas |
| `microduck.py` | Pastel shells over a bare servo spine, flat beak, oversized feet |
| `reachy2.py` | Striped torso, two seven-axis arms, Orbita neck, mobile base |
| `build_models.py` | Entry point, preview renderer |

## How a model reaches the screen

Each joint is an **empty named for its SDK joint** - `left.hip_yaw`, `r_arm.elbow.pitch` - with the
meshes it moves parented underneath. The viewport looks a joint up by name and writes a rotation;
nothing is addressed by index, so a model can gain a part without renumbering anything.

Two details are easy to get wrong and expensive to debug:

**Dots do not survive the trip.** three.js strips `. : / [ ]` out of every node name as it loads, so
`left.hip_yaw` would arrive as `lefthip_yaw`. `common.node_name` writes underscores and the
viewport's `nodeName` applies the same substitution, so both sides keep using the catalogue's
names. The first load of these models failed exactly here, and the symptom was a list of joints
reported missing from a model that plainly contained them.

**Author in parent-local coordinates.** `common.attach` parents without preserving world position,
deliberately: the keep-world-position form needs `parent.matrix_world`, which in a background build
is still the identity until the depsgraph runs. It silently does nothing, and every part lands
wherever its local offset happened to put it.

## Frames

Models are authored **Z-up, facing -Y**, which is Blender's convention. The exporter's Y-up
conversion turns that into the frame the viewport assumes: **X right, Y up, Z forward**. Both
halves are left at their defaults on purpose - turning the conversion off would mean rotating the
loaded root and then correcting every joint axis in the opposite direction.

The SDK itself works in the robotics convention (Z up, X forward, Y left). That conversion happens
in exactly one place, where the duck's world pose is applied in `viewport.js`.

## What is approximate

Pollen publishes no meshes under a licence this project could vendor, so every shape here is
modelled from photographs. Silhouettes, proportions and colours are close; panel lines, fasteners
and the interior of any mechanism are not there at all. See
[docs/kinematics.md](../../docs/kinematics.md) for which *dimensions* are derived rather than known
- a model that looks right is not evidence that a link length is right.
